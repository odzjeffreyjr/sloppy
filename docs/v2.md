# Sloppy v2 — AI Game Agent: Comprehensive Upgrade Plan

> Upgrading from simple HTML game generation to a robust AI agent pipeline that creates high-quality 2D and 3D games with full lifecycle support (start, pause, restart, multiplayer), iterates until games are production-ready, and deploys to your existing GCP infrastructure.

---

## Executive Summary

This plan upgrades the Sloppy platform's core game generation capability across four dimensions:

1. **Rendering Engine Upgrade** — Move from basic Phaser/PixiJS to a dual-engine model: Phaser 3 (2D) + Three.js (3D), with automatic engine selection based on the game concept
2. **AI Agent Loop** — Replace the single-pass generation with a multi-agent iterative pipeline that validates, self-corrects, and only deploys when a game passes all quality gates
3. **Game Lifecycle Contract** — Every game must implement start, pause, resume, restart, and game-over screens natively, built into the SDK contract
4. **Multiplayer Intelligence** — The AI determines if a game concept suits multiplayer, and if so, generates the full multiplayer layer automatically

## Part 1: Technology Stack Decision

### The Dual-Engine Model

| Dimension | 2D Games | 3D Games |
|---|---|---|
| **Engine** | Phaser 3.x | Three.js r165+ |
| **Physics** | Matter.js (built into Phaser) | Rapier3D (WASM, 20KB) |
| **Particles** | Phaser Particles | Three.js Points + custom shaders |
| **UI/HUD** | Phaser DOM + GameObjects | CSS3D overlay on canvas |
| **Audio** | Phaser Sound (Web Audio) | Howler.js |
| **Shaders** | Phaser Pipeline | Three.js ShaderMaterial / post-processing |
| **AI familiarity** | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| **Output quality** | Polished 2D | Console-grade 3D feel |

### Why NOT Unity, Godot, or Babylon

- **Unity**: Requires Editor installation, 10–20 min compile, massive WebGL bundles (80MB+). Not AI-writable.
- **Godot Web Export**: Same compile problem. GDScript is underrepresented in AI training data.
- **Babylon.js**: Excellent but verbose API with less AI training coverage than Three.js. Three.js has 10x more open-source examples in training data.
- **PlayCanvas**: Cloud-based editor dependency, not single-file deployable.

**Phaser 3 + Three.js is the optimal choice** — both are pure JavaScript, CDN-importable, single-file deployable, and massively over-represented in AI training data.

### Quality Ceiling Examples (What's Achievable)

2D with Phaser 3:
- Vampire Survivors-style top-down shooters with particle-heavy effects
- Metroidvania platformers with parallax, dynamic lighting via shaders
- Puzzle games with physics (Angry Birds-style)
- Tower defense with path-finding (A*)
- Match-3, card games, rhythm games

3D with Three.js:
- Low-poly racing games with procedural tracks
- First-person maze/horror games
- 3D puzzle games (Monument Valley-style)
- Endless runners (Temple Run-style)
- Space shooters with bloom/glow post-processing
- Voxel builders (Minecraft-lite)

## Part 2: New Game Lifecycle Contract (SDK v2)

This is the most critical change. Every generated game must implement a full state machine.

### Game State Machine

```
         ┌─────────────────────────────────────────────┐
         │                                             │
    ┌────▼────┐    ┌──────────┐    ┌──────────────┐   │
    │  IDLE   │───▶│  INTRO   │───▶│   PLAYING    │   │
    └─────────┘    └──────────┘    └──────┬───────┘   │
                                          │            │
                                    pause │            │
                                          ▼            │
                                   ┌──────────┐        │
                                   │  PAUSED  │        │
                                   └──────┬───┘        │
                                          │ resume     │
                                          ▼            │
                                   ┌──────────┐        │
                                   │  PLAYING │        │
                                   └──────┬───┘        │
                                          │ game over  │
                                          ▼            │
                                   ┌──────────────┐    │
                                   │  GAME OVER   │    │
                                   └──────┬───────┘    │
                                          │ restart    │
                                          └────────────┘
```

### SDK v2 Contract

```typescript
interface SloppyGameV2 {
  // === Lifecycle ===
  init(container: HTMLElement, config: GameInitConfig): Promise<void>;
  destroy(): void;

  // === State Machine ===
  start(): void;          // IDLE → INTRO → PLAYING
  pause(): void;          // PLAYING → PAUSED (show pause screen)
  resume(): void;         // PAUSED → PLAYING
  restart(): void;        // ANY → PLAYING (reset all state)
  
  // === Screen Rendering (AI must implement each) ===
  renderIntroScreen(): void;    // Title, start button, controls hint
  renderPauseScreen(): void;    // Pause menu: resume, restart, quit
  renderGameOverScreen(score: GameResult): void; // Score, high score, restart CTA
  renderHUD(): void;            // In-game HUD: score, health, timer etc.

  // === State Introspection ===
  getState(): GameState;        // 'idle' | 'intro' | 'playing' | 'paused' | 'gameover'
  getScore(): GameResult;
  
  // === Metadata ===
  readonly metadata: GameMetadata;
  
  // === Multiplayer (conditional) ===
  readonly supportsMultiplayer: boolean;
  multiplayerHooks?: MultiplayerHooks;
}

interface GameMetadata {
  title: string;
  genre: '2d-platformer' | '2d-topdown' | '2d-puzzle' | '2d-arcade' | 
         '3d-firstperson' | '3d-thirdperson' | '3d-racing' | '3d-puzzle';
  engine: 'phaser3' | 'threejs';
  supportsMultiplayer: boolean;
  maxPlayers?: number;
  controls: ControlHint[];
  estimatedPlayTime: string; // e.g. "2-5 min"
}

interface ControlHint {
  key: string;   // e.g. "WASD", "Space", "Click"
  action: string; // e.g. "Move", "Jump", "Shoot"
}

interface GameResult {
  score: number;
  level?: number;
  timeElapsed: number;
  customData?: Record<string, unknown>;
}

interface MultiplayerHooks {
  getInitialState(): Record<string, unknown>;
  applyPlayerInput(playerId: string, input: PlayerInput): void;
  updateState(serverState: Record<string, unknown>): void;
  serializeState(): Record<string, unknown>;
  onPlayerJoin(playerId: string): void;
  onPlayerLeave(playerId: string): void;
}
```

### Why Screens Must Be In-Game

The current architecture likely renders loading/pause overlays in the React shell. This breaks for two reasons:

1. The game canvas (Phaser/Three.js) renders on top of React DOM in fullscreen — React overlays can get z-index conflicts and input-blocking issues
2. Pause/game-over screens need access to game state (current score, player count, etc.) that only the game itself knows

The correct architecture: **the game renders its own screens onto its own canvas/DOM**. The React shell only manages the outer chrome (generate button, feed, etc.).

## Part 3: The AI Agent Pipeline (v2)

This is the core upgrade. Replace single-pass generation with a multi-agent loop.

### Current Pipeline (v1)
```
Prompt → AI generates code → Validate → Store → Serve
                                ↓ fail
                             Reject ❌
```

### New Pipeline (v2)
```
Prompt
  ↓
[Agent 1: Concept Architect]
  → Analyzes prompt
  → Determines: 2D or 3D, genre, engine choice
  → Decides if multiplayer makes sense
  → Writes structured Game Design Document (GDD)
  → Estimates complexity: Simple / Medium / Complex
  ↓
[Agent 2: Technical Planner]
  → Reads GDD
  → Plans exact file structure and code modules
  → Writes pseudocode for each system (physics, rendering, game loop, HUD)
  → Identifies which Phaser/Three.js APIs are needed
  → Creates the "spec" the code agent must follow
  ↓
[Agent 3: Code Generator]
  → Implements the full game from the spec
  → Must use the SDK v2 contract
  → Uses chain-of-thought to reason through each system before writing it
  → Outputs single self-contained HTML file (all JS inline or in one bundle)
  ↓
[Validator: Static Analysis]
  → Parse JS AST
  → Check SDK contract compliance (all required methods present)
  → Check for forbidden APIs (eval, external fetch, localStorage abuse)
  → Check screen implementations (intro, pause, gameover)
  → Check size limits
  ↓ pass / fail + error report
[Validator: Runtime Sandbox Test]
  → Spawn headless Puppeteer instance
  → Load game in sandbox
  → Run automated interaction sequence:
      • init() → wait for intro screen
      • start() → verify playing state
      • pause() → verify pause screen renders
      • resume() → verify game resumes
      • simulate game over → verify gameover screen
      • restart() → verify game resets
  → Capture console errors
  → Screenshot each state for visual review
  ↓ pass / fail + error report
[Agent 4: Debug & Fix Loop]
  → Receives: original spec + code + error report + screenshots
  → Diagnoses root cause
  → Applies targeted fix
  → Returns to Validator
  → Max 5 iterations before escalating to human review
  ↓ all clear
[Agent 5: Polish Pass]
  → Reads final working code
  → Checks: visual quality, game feel, screen polish
  → Applies improvements: better colors, smoother animations, juicier effects
  → Does NOT change game logic — only aesthetics
  ↓
[Multiplayer Injector] (if supportsMultiplayer: true)
  → Reads game code
  → Injects multiplayer SDK connection
  → Implements multiplayerHooks
  → Runs multiplayer validation pass
  ↓
[Final Build]
  → Minify + bundle
  → Generate config.json
  → Upload to GCS
  → Create DB record
  → Return gameId to frontend
```

### Agent Prompting Strategy

Each agent uses a specialized system prompt. The key insight is **chain-of-thought with explicit reasoning checkpoints**:

```
Agent 3 (Code Generator) system prompt pattern:

"You are writing a complete Phaser 3 browser game.
Before writing ANY code, reason through:
1. What is the game loop structure?
2. What Phaser scenes do I need?
3. How does the state machine map to Phaser scene transitions?
4. What data needs to persist across restarts?

Then write the code section by section, explaining each section
before implementing it. The game MUST implement init, start, pause,
resume, restart, renderIntroScreen, renderPauseScreen, and 
renderGameOverScreen. Test your implementation mentally before finalizing."
```

### The Debug Loop in Detail

```typescript
interface DebugContext {
  originalSpec: GameSpec;
  currentCode: string;
  validationErrors: ValidationError[];
  runtimeErrors: RuntimeError[];
  screenshots: Record<GameState, string>; // base64
  iterationCount: number;
}

// Agent 4 prompt includes:
// - The exact error message
// - The line of code that failed
// - The screenshot of what rendered vs what was expected
// - The original spec requirement that wasn't met
// - Instruction to FIX ONLY the failing part, not rewrite everything
```

This targeted approach prevents the "rewrite loop" where an AI fixes one thing and breaks three others.

## Part 5: 3D Game Generation Strategy

3D games with Three.js require a different generation approach than 2D.

### The 3D Template Library

Instead of generating Three.js from scratch every time, the AI works from **genre templates** that have the boilerplate pre-solved. The AI fills in the game-specific logic.

```
packages/runtime-sdk/src/templates/3d/
  fps-template.js        ← Camera, pointer lock, collision detection solved
  racing-template.js     ← Track, physics, lap counter solved
  endless-runner-template.js ← Procedural track, obstacle spawning solved
  puzzle-3d-template.js  ← Object interaction, camera orbit solved
  tower-defense-3d.js    ← Grid system, pathfinding, camera solved
```

Each template provides:
- Correct Three.js scene setup (renderer, camera, lighting, shadows)
- The game loop integrated with the SDK v2 contract
- Post-processing pipeline (bloom, SSAO for quality feel)
- Touch/keyboard controls
- Mobile-responsive canvas sizing

The AI then receives the template + GDD and fills in: game objects, rules, scoring, visual theme.

### Visual Quality Defaults for 3D

Every Three.js game must initialize with this quality baseline:

```javascript
// Always included in 3D games:
renderer.shadowMap.enabled = true;
renderer.shadowMap.type = THREE.PCFSoftShadowMap;
renderer.toneMapping = THREE.ACESFilmicToneMapping;
renderer.toneMappingExposure = 1.0;

// Post-processing (using Three.js EffectComposer):
const bloomPass = new UnrealBloomPass(
  new THREE.Vector2(window.innerWidth, window.innerHeight),
  0.4,  // strength
  0.4,  // radius
  0.85  // threshold
);
```

This alone makes Three.js games look dramatically better.

### AI Prompt for 3D Games

The 3D prompt uses a **constraint-first approach** — the AI is given what NOT to do (which is more effective for quality):

```
"You are building a 3D browser game with Three.js.

VISUAL QUALITY RULES:
- ALWAYS enable shadows and ACES filmic tone mapping
- ALWAYS add ambient + directional light, never just ambient alone
- NEVER use MeshBasicMaterial for game objects (no lighting response)
- ALWAYS use MeshStandardMaterial or MeshPhysicalMaterial
- ALWAYS add fog to give depth
- For any game object representing a character: minimum 8-sided geometry

PERFORMANCE RULES:
- NEVER create new THREE objects inside the game loop (pre-allocate)
- ALWAYS dispose geometry and materials in destroy()
- Target 60fps on mid-range mobile: max 10,000 triangles total

GAME FEEL RULES:
- Every player action must have a visual response within 1 frame
- Camera must have slight lag/smoothing (lerp factor 0.1)
- Score changes must trigger a brief screen flash or number pop"
```

## Part 6: Multiplayer Intelligence

### How the AI Decides on Multiplayer

The Concept Architect agent evaluates multiplayer suitability:

```typescript
interface MultiplayerAnalysis {
  suitable: boolean;
  reason: string;
  suggestedMode: 'competitive' | 'cooperative' | 'versus' | null;
  maxPlayers: 2 | 4 | 8 | null;
  syncStrategy: 'state-sync' | 'input-relay' | 'lockstep' | null;
}

// Examples:
// "Endless runner" → { suitable: true, mode: 'competitive', maxPlayers: 4, sync: 'state-sync' }
// "Puzzle game" → { suitable: true, mode: 'cooperative', maxPlayers: 2, sync: 'state-sync' }
// "Solitaire card game" → { suitable: false, reason: 'Single-player by design' }
// "Tower defense" → { suitable: true, mode: 'cooperative', maxPlayers: 2, sync: 'state-sync' }
```

### Multiplayer Architecture Per Sync Strategy

**State Sync** (most games — recommended default):
- Server holds authoritative state
- Clients send inputs, server applies them, broadcasts new state
- 50–100ms latency acceptable, good for turn-based or slower games

**Input Relay** (fast action games):
- Server relays inputs between clients
- Each client simulates locally + reconciles
- Required for <16ms feel games (platformers, shooters)

**Lockstep** (pure competitive):
- All clients step together
- Deterministic simulation required
- Best for strategy/puzzle

The AI must correctly identify which strategy fits the game and implement it. The Multiplayer Injector agent handles the injection into existing working single-player code.

## Part 9: Critical Engineering Decisions

### 1. Single File vs Module Bundle for Games

**Decision: Single self-contained HTML file**

All game code + inlined dependencies via CDN imports at the top. No module bundler needed.

```html
<!DOCTYPE html>
<html>
<head>
  <script src="https://cdn.jsdelivr.net/npm/phaser@3.80.1/dist/phaser.min.js"></script>
  <!-- OR for 3D: -->
  <script src="https://cdn.jsdelivr.net/npm/three@0.160.0/build/three.min.js"></script>
</head>
<body>
  <script>
    // All game code here
    window.SloppyGame = { ... }
  </script>
</body>
</html>
```

This means zero build step, instant serve from GCS, and the entire game is version-pinned to a CDN URL.

### 2. Puppeteer in game-builder: Cold Start Performance

Puppeteer adds ~2–4 seconds to validation. Mitigate with:
- Keep a warm Puppeteer instance pool (2 instances per game-builder pod)
- Run validation async — return `gameId` immediately when code generation is done, stream validation results via SSE
- Show "Testing your game..." phase in the UI with live screenshots as they're captured

### 3. Iteration Loop Token Budget

Each iteration of the debug loop costs tokens. Hard limits:
- Max 5 iterations per game
- If iteration 5 fails: mark game as `needs_review`, notify (or silently drop for now)
- Log all failed games for manual review to improve prompts over time

### 4. 3D Performance on Mobile

Three.js games must be tested at 720p equivalent on the Puppeteer validator. Add a performance check:
- Measure average FPS during 5 seconds of simulated gameplay
- Reject if FPS < 30 (fail the iteration, trigger debug loop with performance error)

### 5. The PostMessage Bridge Security

The game iframe uses `sandbox="allow-scripts"` so it can't access parent DOM. PostMessage is the only communication channel. Both sides must validate message origin:

```typescript
// In game (inside iframe):
window.parent.postMessage({ type: 'sloppy:state', state: 'paused' }, 
  'https://sloppy.app'); // Exact origin only

// In React shell:
```

The upgraded Sloppy platform is a **fully autonomous game factory** that:

1. Takes a natural language prompt
2. Architecturally plans a high-quality 2D (Phaser 3) or 3D (Three.js) game
3. Generates production-quality code through a specialized multi-agent pipeline
4. Robotically tests the game through its entire state machine using headless Chrome
5. Self-corrects up to 5 times if anything fails
6. Polishes the visual quality on the final passing build
7. Auto-determines if multiplayer makes sense and injects it
8. Deploys to GCS and serves instantly in the browser
